# Competitor Research Starter contract v1.0.0

Frozen before implementation: 2026-09-21. Endpoint behavior checked against SocialKit API origin/main on that date. This spec defines the base job and the n8n monitor's normalized items.

- Node.js 22+; no runtime dependencies, account system, dashboard, or mandatory telemetry.
- One to three distinct public YouTube channel or Instagram profile URLs. Reject video URLs, credentials, unsupported hosts and malformed URLs before sending a request.
- Default ten items/profile; configurable integer 1–50. Fetch **Instagram Reels only**, using `/instagram/channel-reels` (`data.items`), and YouTube `/youtube/videos` (`data.results`). Never fetch both Instagram posts and Reels by default. No client pagination; an Instagram continuation is noted, never followed. YouTube `full_details=false`; dates/descriptions can be missing.
- Base collection needs no per-item stats, transcripts or LLM calls. These are deliberately outside v1's command; a downstream user may opt into their own separately budgeted analysis. Never promise likes/comments for YouTube lists.
- Sequential requests; at most one retry after a 429 or 5xx, never retry authentication or validation failures. Defaults: six HTTP attempts, six reserved credits, 60 seconds/request, 240 seconds/job, retry delay <=2 seconds. Hard supported ceilings: six attempts, 18 reserved credits, 90 seconds/request, 540 seconds/job. Reserve estimated maximum credits **before each attempt**, including timed-out/failed attempts. YouTube list charge: one credit per 50 returned items (at least one); Instagram Reels: one per 20 (at least one). Default three-profile first pass models three credits, worst case with one retry each six. Expose actual `X-Credits-Remaining` observations, not a fabricated charged-credit header or spend inferred across concurrent account activity. Costs remain modeled under the documented endpoint contract; a malformed over-limit response stops further requests.
- An unavailable/private profile or rejected response produces an explicit failure beside successful profiles. Authentication/credit exhaustion stops subsequent requests. Exit 0 = all profiles usable (including valid empty lists), 2 = report with partial/all collection failures, 1 = invalid configuration or local I/O failure.
- JSON `schemaVersion: "1.0.0"`: collection start/end; frozen limits; per-profile status/error/warnings; normalized items; platform/content-group top-three rankings; request ledger and modeled reservation total. Items include `id`, `platform`, `contentType`, `profileUrl`, `sourceUrl`, `title`, `description`, `publishedAt`, `fetchedAt`, and `metrics` (views/likes/comments nullable). ID is `youtube:<11-char-video-id>` or `instagram:<shortcode>`. Reject mismatching ID/source URL, wrong returned profile identity, and Instagram author mismatch. Deduplicate identical IDs. Preserve numeric zero from API, missing/non-numeric/negative values as null; note upstream APIs can themselves default unknown metrics to zero. Never invent publication timestamps from relative strings.
- YouTube content is `video`, or `short` only with explicit source evidence; Instagram content is `reel` (mixed/unexpected types rejected with warnings). Sort top performers by known views descending, ties by stable ID, within platform/content type. Null views do not rank. Rankings describe only the collected sample; no cross-platform leaderboard, engagement rate, reach equivalence or claims of complete recent history.
- Write useful Markdown plus JSON containing source links, recent sample, top performers, unknowns, failures, warnings and budget ledger. Text is escaped for Markdown. Do not store keys, CDN media URLs, request headers or raw error bodies. A real public-profile example is published only after a verified paid run; fixtures are conspicuously synthetic.

## n8n delivery contract

Versioned importable JSON uses built-in HTTP Request nodes and the same bounded endpoints/schema. Manual and schedule triggers; up to three profiles and ten items/profile, <=3 API requests/credits per run (no inline retries), ten-minute workflow timeout. Persistent PostgreSQL state (schema supplied) stores destination-scoped delivered IDs and one pending outbox. A 15-minute atomic lease prevents overlapping collection/delivery; it exceeds execution timeout. Reclaim only expired leases. HTTP sends have 30-second timeouts. Confirm Slack HTTP 200 **and** `ok:true` before atomically marking all outbox IDs delivered and clearing it. Retain delivered IDs indefinitely by default; operators may intentionally prune history, accepting old-item redelivery.

A failed/ambiguous Slack send retains the exact pending outbox for the next scheduled/manual retry, without re-collecting or spending API credits. Delivery is at least once: if Slack accepts a message but acknowledgement/state commit is lost, a duplicate may occur; never claim exactly once. Use a stable digest ID in the message. Failure/empty collection leaves no delivered marks. Empty new-item runs do not send Slack. Partial profile failures appear in the digest accompanying available new items and in execution output; an all-failed run fails visibly without a noise-only Slack message. Credentials stay in n8n credential storage, with no exported secret IDs. No mandatory AI; any later AI enrichment must preserve IDs, sources, facts and delivery ordering.
